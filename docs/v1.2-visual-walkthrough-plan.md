# V1.2 视觉走查计划（Visual Walkthrough Plan）

> 状态：待执行
> 目标：验证 V1.2 已交付的前端 UI（价格提醒、用户偏好、Swap 代币选择器收藏区）在真实运行环境下「能用、好看、无回归」，并修复走查发现的 bug。
> 范围：只覆盖 V1.2 新增/改动的 3 处前端面，不扩大到 V1.0/V1.1 已有页面（除非走查顺带发现明显回归，单独记录）。

## 0. 背景与结论先行

- V1.2 三个交付项均已合入并通过 `tsc`/`build`/`lint`：
  - 价格提醒（`/alerts`）— `apps/web/src/components/alerts/AlertsView.tsx`
  - 用户偏好 + 收藏管理（`/settings`）— `apps/web/src/components/preferences/SettingsView.tsx`

- **关键事实（决定走查方式）**：全仓库无 Playwright/Cypress/Puppeteer，前端无任何自动化浏览器测试基建。因此本走查采用「本地起前后端 → 逐页手动/半自动验证」的清单形式，不做一键截图脚本。
- 后端两个新模块（Alerts/Preferences）已在 V1.2 执行阶段通过 jest 单测 + 端到端冒烟（preferences upsert/读取、alerts 创建/check 触发、状态流转），本轮**重点不在后端逻辑，而在前端渲染与交互**。

## 1. 走查前置：环境准备

### 1.1 依赖现状（已核实）
- 前端 `apps/web`（Next.js，端口 3000）；后端 `apps/api`（NestJS，端口 3001）。
- 前端调用偏好/提醒接口依赖环境变量 `NEXT_PUBLIC_API_BASE_URL`（`apps/web/src/services/preferences.ts` 与 `services/alerts.ts` 的 `is*ApiConfigured()` 均以它为开关）。

### 1.2 启动步骤（走查开始前逐条确认）
1. 确认 PostgreSQL 已启动（V1.2 后端依赖 PG；若无则按历史方式用 Docker 起 PG16 + Redis）。
2. 后端：`cd apps/api && rm -rf dist && pnpm build && node dist/main.js`（用 `node dist/main.js` 非 watch，规避安全删除守卫）。
3. 前端：`cd apps/web && NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:3001 pnpm dev`。
4. 浏览器打开 `http://localhost:3000`，连接一个测试钱包（Metamask 或开发者模拟）。

> ⚠️ 本机已知坑（务必遵守）：`http_proxy` 环境变量会劫持 `127.0.0.1` 探测；探测本机服务必须禁用代理（`curl --noproxy '*'` 或前端请求不经过代理）。启动前先 `(Get-PSDrive C).Free` 确认 C 盘空间，避免 `ENOSPC`。

## 3. 已识别的薄弱点（走查时重点盯，可能出问题）

1. **`favoritePending` 是全局布尔**（`TokenSelector.tsx:199`）：任一收藏操作 pending 时**所有**星标都禁用。属于可接受的 UX 简化，但走查时留意是否造成「点 A 币时 B 币星标闪灰」的观感问题；若明显，记录为可选优化。
2. **Alerts 页 `notifyMethod` 未在前端暴露**：后端 `PriceAlert` 有 `notifyMethod` 字段，但前端表单未提供选择（走查时确认是否影响体验；不属 bug，属未接入项）。
3. **收藏「冷门币」在 Swap 选择器不显示**（A8）：这是设计决策（收藏区只展示当前链 `chainTokens` 里能匹配到的），走查确认「不显示但不报错」即可，不做额外展示。
4. **`SettingsView` 的 `useEffect` 回填**：`prefs.data` 每次变化都会重置表单（含保存成功后）。走查确认「用户正在编辑时若后端 refetch 不会突然覆盖输入」——正常场景不会 refetch，但需留意。
5. **后端未启动时前端表现**：`NEXT_PUBLIC_API_BASE_URL` 未设或后端挂了时，应走「service not connected」/错误空态而非白屏。走查 B2/C1 已覆盖，但补充确认无未捕获异常导致页面崩溃。

## 4. 执行方式（谁来做、怎么做）

### 4.1 分工建议
- **走查主体**：派一个前端工程师（fresh spawn，不带旧上下文，用「新眼」走查）。
- **后端配合**：走查需要 PG + 后端真实起来；如后端未起，先由 devops/后端同学按 §1.2 启动，或走查工程师自行 `node dist/main.js` 启动（历史已验证可行）。
- **独立复核**：走查工程师产出的「通过/失败 + 截图 + bug 清单」由 lead（我）独立抽查关键项（尤其 A3-A5 星标交互、C8 跨面滑点联动）。

### 4.2 产出物
1. 一份填好的走查清单（上表逐项 ✅/❌）。
2. 发现的 bug 列表（每条含：页面 / 复现步骤 / 预期 vs 实际 / 严重级 / 建议修法）。
3. 关键页面截图（至少：Swap 选择器含收藏区、Alerts 有提醒列表态、Settings 已保存态）。
4. 修复后的 commit（如有 bug）。

### 4.3 验收标准（Definition of Done）
- §2 清单 A1-A9、B1-B10、C1-C8、D1-D3 全部为 ✅，或有明确「记录为已知项、不阻塞」的结论。
- 发现的 P0/P1 bug（导致功能不可用或明显交互错误）已修复并通过回归；P2 视觉瑕疵可延后但须登记。
- 后端两个模块的单测仍然全绿（走查不引入回归）。

## 5. 风险与回滚

- **环境风险**：本机 C 盘空间紧张、代理劫持、PG/Docker 依赖。启动失败时按 §1.2 的已知坑处理，不阻塞走查结论（可在「后端未起」状态验证 B2/C1 空态）。
- **范围风险**：走查可能顺带发现 V1.0/V1.1 既有页面的回归——单独记录，不在本轮修复（除非是 V1.2 改动直接引起）。
- **回滚**：走查只读 + 截图 + 记录，不直接改业务代码；需要修复时单独开 commit，便于 revert。
