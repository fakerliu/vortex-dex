## 〇、版本切分决策（先读，重要）

用户确认 V1.3 想做四件事，但它们的**性质截然不同**，强行塞进一个版本会稀释焦点。本规划按性质切成两个独立版本：

| 版本 | 内容 | 性质 | 能否立即派工 |
|------|------|------|-------------|
| **V1.3**（本文档） | 拆单性能根治 + 站内通知中心 + 价格提醒推送抽象 | 纯工程、无合约依赖、可立即落地 | ✅ 是 |
| **V1.4 专项**（另立文档） | Limit Order / DCA / Cross-chain | 需自有合约或链下 keeper，架构级新增 | ❌ 需先做架构决策 + 安全审计 |

> 理由：项目一直遵循「非托管、复用官方 Router、无自有合约」原则（`contracts/` 当前 0 个 .sol）。合约类功能是架构级转折，必须先出「自有合约 vs 链下 keeper」决策文档 + 安全评估，不能当普通功能任务派工。**V1.3 只做纯工程三块；V1.4 专项单独开规划。**

## 二、模块 1：拆单性能根治

### 2.1 现状（已核实，精确到行）

`apps/api/src/modules/swap/split.service.ts` 的 `binarySearchCap`（约 574-630 行）：

- 已有「快速路径」：`candidate.quote.priceImpact ≤ threshold` 时直接返回上界，跳过二分（第 587-590 行）。常见场景已免二分。
- **慢路径本质**：一旦需要二分，`while` 循环每次 `mid` 探测调 `quoteCandidateAt` → **一次 RPC 往返**。极严阈值 + 大额时约 48 次探测 × 多池 = 数分钟。
- revert 已修复（4c62f48）：探测超池容量时收缩上界，不再 500。

### 2.2 根治方案（分池类型，不对 CL 池硬上解析式）

**关键事实**：只有 **classic 池（恒定乘积 AMM）** 能用解析式免二分；**CL 池（集中流动性）无法解析式**，只能并行探测或异步化。

| 方案 | 适用 | 原理 | 预期效果 |
|------|------|------|---------|
| **A. classic 解析式免二分** | Aerodrome classic / Uniswap V2 风格池 | 用池储备 `reserve0/reserve1` + fee，直接解恒定乘积方程得「不超阈值最大 amountIn」，无需 RPC 探测 | classic 池二分 48 次 RPC → 0 次 |
| **B. CL 池并行探测** | Aerodrome CL / Uniswap V3 | 把二分探测改为「多金额点并行 RPC」（`Promise.all`），或预采样若干候选金额一次并发 | CL 池 48 次串行 → 1-2 轮并发 |
| **C. 异步化（可选，架构级）** | 全局 | prepare 返回 job id，前端轮询/SSE，彻底解除 HTTP 超时 | 根治超时，但改动大 |

**V1.3 建议落地 A + B**，C 作为可选增强（需前端配合轮询，改动大，单独评估）。

### 2.3 前置调研（派工前必须确认，否则 A 方案落不了地）

A 方案的前提是「classic adapter 能拿到池的真实 reserve + fee」：

1. `apps/api/src/dex/aerodrome/aerodrome-classic.adapter.ts` 的 `getQuote` 是否已读 `reserve0/reserve1`？能否暴露一个 `getReserves(pool)` 或 `getQuote` 返回里含储备？
2. classic 池的 fee 从哪拿（池合约 `fee()` 调用，还是常量）？
3. 恒定乘积公式用 BigInt 定点算，价格影响 `priceImpact = 1 - amountOut/(amountIn×spotPrice)`，需与现有 `quote.priceImpact` 口径一致，否则拆出的金额与链上实际不符。

> 这是「解析式免二分」的**技术可行性前置**，V1.3-1a 任务应先做这个只读调研，再决定 A 方案是「解析式」还是「降级为并行探测」。

### 2.4 任务拆分

| # | 任务 | 内容 | 依赖 |
|---|------|------|------|
| V1.3-1a | 调研 classic 储备/fee 可得性 | 读 adapter，确认能否解析式算价格影响；产出可行性结论 | 无 |
| V1.3-1b | classic 解析式免二分 | 在 `binarySearchCap` 加 classic 快速解析路径（可复用则复用）；CL 保留二分 | V1.3-1a |
| V1.3-1c | CL 池并行探测 | `quoteCandidateAt` 多金额点 `Promise.all` 并发 | V1.3-1a |
| V1.3-1d | 真实链上性能复测 | 大额拆分前后耗时对比（复用 V1.1 冒烟脚本） | V1.3-1b/1c |

## 三、模块 2：站内通知中心

### 3.1 现状（已核实）

`apps/api/src/modules/alerts/alerts.service.ts` 的 `checkPriceAlerts`（145-193 行）：命中后仅 `status=triggered` + `triggered_at` 更新，**不落任何通知记录**。`notifyMethod` 只是字段校验（`in_app/email/webhook`），无发送实现。

### 3.2 功能定义

- 提醒触发时，**写一条站内通知记录**（用户可查「我的通知」）。
- 前端新增「通知中心」入口（顶栏铃铛 + 未读角标）+ 通知列表页 `/notifications`。
- 通知字段：用户、类型（价格提醒触发）、标题、正文、关联 token/提醒 id、已读状态、时间。
- 未读角标：顶栏显示未读数（前端轮询或读接口）。

### 3.3 数据模型（新增，Prisma）

```prisma
model Notification {
  id           String   @id @default(cuid())
  user_address String   // 小写规范化
  type         String   // price_alert_triggered（预留其他类型）
  title        String
  body         String
  alert_id     String?  // 关联价格提醒（可空）
  token_address String? // 关联 token（可空）
  read         Boolean  @default(false)
  created_at   DateTime @default(now())

  @@index([user_address, read])
  @@index([user_address, created_at])
  @@map("notifications")
}
```

### 3.4 API（挂 /api/v1）

- `GET /notifications?user=:address` — 列出用户通知（未读优先、时间降序）
- `PATCH /notifications/:id/read` — 标记已读
- `POST /notifications/read-all` — 全部已读（body: `{ userAddress }`）
- `GET /notifications/unread-count?user=:address` — 未读数（供顶栏角标）

|---|------|------|------|
| V1.3-2a | 后端 Notification 模块 | schema + service + controller + 触发落库（接 `checkPriceAlerts`）+ 单测 | 无 |
| V1.3-2b | 前端通知中心 | 顶栏铃铛角标 + `/notifications` 列表页 + 已读交互 | V1.3-2a |

## 四、模块 3：价格提醒推送抽象（可插拔通知渠道）

### 4.1 定位

V1.2 的 `notifyMethod`（`in_app/email/webhook`）目前只是字段。V1.3 把它做成**可插拔通知渠道**，但**只落地站内**（通知中心），email/webhook 留接口抽象，不接真实第三方（本机代理受限 + 需 API key）。

### 4.2 设计

- 定义 `NotificationProvider` 接口：`send(notification): Promise<void>`。
- 内置实现：`InAppProvider`（写 Notification 表，即模块 2 的地基）。
- `EmailProvider` / `WebhookProvider` 留接口 + 配置占位（不实现发送，或实现但默认关闭）。
- 触发时按 `notifyMethod` 分派：`in_app` → 落站内通知；`email/webhook` → 走对应 provider（V1.3 未接时降级为站内 + 记录「渠道未接入」）。

### 4.3 任务拆分

| # | 任务 | 内容 | 依赖 |
|---|------|------|------|
| V1.3-3a | 通知渠道抽象层 | `NotificationProvider` 接口 + InAppProvider + 分派逻辑 + 单测 | V1.3-2a |
| V1.3-3b | email/webhook 接口占位 | 抽象 + 配置占位 + 未接入降级策略 | V1.3-3a |

## 五、执行计划（建议顺序）

**依赖关系**：模块 1（拆单性能）与模块 2/3（通知）完全独立，可**两线并行**。模块 3 依赖模块 2。

```
线 A（拆单性能）：V1.3-1a → 1b → 1c → 1d
线 B（通知）：    V1.3-2a → 2b → 3a → 3b
```

- **并行派工**：线 A 派 1 个后端工程师（串行做 1a→1d）；线 B 派 1 个后端 + 1 个前端。
- **共享文件隔离**：线 A 只碰 `split.service.ts` 及 dex/adapter 相关；线 B 碰 `alerts` + 新增 `notifications` 模块 + schema（Notification 表）+ 前端。两边交集只有 `alerts.service.ts`（线 B 的「触发落库」要在 `checkPriceAlerts` 里加通知写入）——这个共享文件由 team lead 提前改好或明确归属，避免冲突。
- **教训复用**：并行派工前先定死契约文档（模块 2/3 需 `docs/v1.3-notification-contract.md`）；明令「不要 git add -A」；同一 bug/模块不留「旧 worker 续接 + 新 worker 派工」两条线。

## 八、风险

1. **解析式免二分的前提未验证**：若 classic adapter 拿不到真实 reserve/fee，方案 A 降级为「并行探测」（1c），仍有性能收益但不达「零 RPC」。→ 用 V1.3-1a 调研先堵住这个风险。
2. **CL 池并行探测仍受 RPC 速率限制**：本机代理 + 公共 RPC 可能限速，并发数需节制。
3. **通知中心引入新表**：需迁移，且 `checkPriceAlerts` 触发落库要幂等（同一提醒不要重复发通知——triggered 状态本身就是幂等闸，需确认）。
4. **共享文件冲突**：线 A/B 若都碰 `alerts.service.ts`，需提前隔离（见 §五）。
