## 〇、决策前提（技术负责人已拍板，直接采信）

1. **路线**：走「自有合约」终极形态（学 1inch/Matcha），分两步落地。
   - **第一阶段（本文档聚焦）**：链下 keeper 跑通全流程——订单存后端 PostgreSQL，keeper 盯价、满足即成交。
   - **第二阶段（仅预留）**：订单挂单迁到链上合约 + 执行者激励。
2. **资金托管**：下单**不锁币**，成交时才从用户钱包划走，复用现有 allowance 授权模型（`user → Router`）。
3. **范围**：先只做「限价买单」（limit buy：tokenOut 价格跌到 ≤ 目标价时，用 amountIn 买入 tokenOut）；卖单镜像逻辑，预留接口。
4. **执行机制**：后端 keeper 定时轮询盯价，满足触发成交，复用现有 Swap 执行能力。

---

## 一、核心结论（TL;DR，先读这一段）

1. **执行签名模型推荐「用户预签 + keeper 广播」**，而非「keeper 持钥签名」。这是本文最关键的一条决策，理由在 §五展开：
   - 现有官方 Router（Aerodrome Classic/CL、Uniswap V3）的 `swapExactTokensForTokens / exactInput` 一律从 `msg.sender` 拉 tokenIn（`transferFrom(msg.sender, …)`）。
   - 若 keeper 用自己的私钥签名，`msg.sender = keeper`，Router 只会从 **keeper** 钱包划币，**动不到用户已授权给 Router 的额度**——「keeper 持钥」与「复用现有 allowance（user→Router）+ 成交时从用户钱包划走」在技术上**互相矛盾**。
   - 因此第一阶段让**用户下单时预签一笔成交交易**（`from = user`、`recipient = user`、`amountOutMin = 限价`），keeper 只负责在价格满足时**广播这笔已签名的交易**。广播 raw tx 本身**不需要任何私钥**（`eth_sendRawTransaction`），Gas 由 `from=user` 承担。
   - 结论：**第一阶段不存在「执行私钥」这个高风险面**；私钥风险整体推迟到第二阶段（自有合约的 filler/settler 激励）才出现，届时再引入 HSM/KMS 等托管方案。
2. **触发判定复用报价引擎的 `amountOut`，而非 MarketService 的 USD 价**：限价单的「限价」本质是 `amountIn / minAmountOut`（tokenIn 每 tokenOut）。触发条件 = `quoteBest(amountIn).amountOut >= min_amount_out`，与成交、与预签交易的 `amountOutMin` 三者**同源同口径**，杜绝「盯价用 USD、成交用 DEX 报价」的误触发。MarketService 的 USD 价仅用于展示/通知文案。
3. **幂等三道闸**：状态机 CAS 抢占 → 确定性 tx hash（同一份签名字节只产生同一个 tx）→ `swaps.tx_hash` 唯一约束。
4. **模块落位**：新建独立 `limit-order` 模块（不挂在 swap 下），单向依赖 Swap/Dex/Notifications/Analytics，不构成循环。
5. **数据模型**：新增 `LimitOrder` 表；金额 `Decimal(78,0)`，目标价比率 `Decimal(78,18)`（与 `price_alerts.target_price` 一致），另存 `min_amount_out`（原始大整数）作为触发/成交/预签交易三处共用的**唯一权威值**。

## 二、系统分层与模块落位

### 2.1 落位结论

新建模块 `apps/api/src/modules/limit-order/`，**不挂在 swap 下**。理由：

- `swap` 是「一次性交易」的即时执行域；`limit-order` 是「订单生命周期 + 常驻盯价 + 延迟成交」的订单域，状态机、API、后台循环都不同，混在一起会污染 swap 的单向数据流。
- 限价单最终（第二阶段）要迁到链上合约，届时 order 域会拥有自己的 on-chain 语义，独立模块便于替换执行器实现。

### 2.2 六层视图（在现有单体中的位置）

```
Frontend (apps/web)         limit-order 页面 / hooks（限价下单、列表、撤单、签名）
        │  HTTP 统一信封
        ▼
Backend (apps/api, NestJS 单体)
  modules/limit-order/   ★ 新增：controller + service + keeper + executor 抽象
        │  单向依赖（无环）
        ├──► modules/swap/        SwapService.prepare / tryReadReceipt（复用）
        ├──► dex/                 DexPoolService.quoteBestForChain（盯价报价）
        ├──► modules/notifications/  NotificationDispatcher（成交/撤单通知）
        └──► modules/analytics/   EventCollectorService（可选埋点）
        │
  chain/                ChainRpcService（补 nonce/gas、广播 raw tx）
  prisma/               LimitOrder 表（PostgreSQL）
        ▼
Base 链（8453/84532）   用户钱包签名 → 后端广播；Router 从 user 划币
```

### 2.3 模块职责表

| 模块/文件 | 职责 | 依赖方向 |
| --- | --- | --- |
| `limit-order.controller.ts` | REST：下单 / 提交签名 / 列表 / 详情 / 撤单 | → service |
| `limit-order.service.ts` | 订单 CRUD + 状态机 CAS + 签名校验 + 派生 `min_amount_out` | → Prisma、DexPoolService、Notifications |
| `limit-order.types.ts` | DTO、状态机常量、`LIMIT_ORDER_STATUS_TRANSITIONS` | 无 |
| `limit-order.signer.ts` | 组装「待签交易」（nonce/gas/deadline）+ 校验提交的签名交易（recover 地址、比对 calldata） | → ChainRpcService、calldata |
| `limit-order-keeper.service.ts` | `setInterval` 盯价循环 + 触发判定 + 调用执行器 + 回执对账 | → service、executor、SwapService.tryReadReceipt |
| `limit-order-executor.ts` | 执行器接口 `LimitOrderExecutor` + Phase1 `PreSignedTxExecutor`（广播） | → ChainRpcService |
| `limit-order.module.ts` | 装配，`exports` 供测试 | imports Swap/Dex/Notifications/Analytics |

### 2.4 避免循环依赖（项目多次踩坑，必须单向注入）

现有依赖链：`SwapModule → MarketModule → AlertsModule → NotificationsModule`（MarketService 注入 AlertsService 做惰性触发，单向）。

新增 `LimitOrderModule` 只做**单向消费**，绝不反向被上述模块注入：

```
LimitOrderModule ──imports──► SwapModule（需 export SwapService）
                ──imports──► DexModule（DexPoolService）
                ──imports──► NotificationsModule（NotificationDispatcher）
                ──imports──► AnalyticsModule（可选 EventCollectorService）
```

- 没有任何现有模块 import LimitOrderModule → 无环。
- **对 SwapModule 的唯一改动**：在 `SwapModule.exports` 中增加 `SwapService`（一行），使 `prepare()` / `tryReadReceipt()` 可被复用。若不想改 SwapModule，则 `limit-order` 自行 import DexModule + AnalyticsModule + MarketModule 并组合自己的「限价 prepare」；但推荐前者（复用成熟逻辑、不重复造轮子）。
- `SwapService.prepare()` 内部已把 `recipient` 固定为 `user`（见 `swap.service.ts` buildTransaction），这正是限价单需要的语义（tokenOut 回用户钱包），**无需改动**。

## 三、数据模型（Prisma `LimitOrder`）

### 3.1 字段设计

```prisma
// ---------- N. 限价单（V1.4 Limit Order，Phase 1 链下 keeper） ----------
model LimitOrder {
  id              String    @id @default(cuid())
  user_address    String    // 小写规范化（下单人 / maker）
  chain_id        Int       // 8453 / 84532

  // 方向：buy（限价买单，V1.4 先做）/ sell（卖单镜像，预留）
  direction       String    // "buy" | "sell"

  // 交易对：tokenIn = 用户付出的币，tokenOut = 用户买入的币
  token_in        String    // 小写规范化
  token_out       String    // 小写规范化

  // 金额（链上原始大整数，Decimal(78,0)，禁 Float）
  amount_in       Decimal   @db.Decimal(78, 0) // 固定输入（exactInput 语义）
  min_amount_out  Decimal   @db.Decimal(78, 0) // 最少输出（限价，权威触发/成交值）

  // 目标价（比率，十进制字符串，Decimal(78,18)）：tokenIn 每 tokenOut 的「最高接受价」
  // 仅用于展示 + 粗筛，触发判定以 min_amount_out 为准。
  limit_price     Decimal   @db.Decimal(78, 18)

  // 滑点（bps）：下单时预留，Phase 1 限价单「限价即 amountOutMin」，滑点主要用于
  // 展示层与 Phase 2 撮合者对冲的参考，默认 0。
  slippage_bps    Int       @default(0)

  // 生命周期
  status          String    @default("pending") // pending / triggered / filled / cancelled / expired / failed
  expires_at      DateTime? // 过期时间（可空=永不过期，但预签 deadline 仍必须有上界，见 §五）
  created_at      DateTime  @default(now())
  updated_at      DateTime  @updatedAt
  triggered_at    DateTime? // 价格首次满足（keeper 抢占）时间
  filled_at       DateTime? // 成交（回执成功）时间

  // 成交结果
  swap_id         String?   // 关联 swaps.id（成交后回填）
  tx_hash         String?   // 成交交易哈希（小写；与 swaps.tx_hash 冗余，便于订单侧直查）
  failure_reason  String?   // 失败原因（revert / nonce 失效 / 余额不足 / allowance 不足）

  // Phase 1：用户预签的成交交易（raw 十六进制，见 §五）
  // 无签名时订单处于 pending 但「未武装（unarmed）」，keeper 不会触发它。
  signed_swap_tx     String? // 预签的 swap 交易 raw hex（from=user, recipient=user）
  signed_approval_tx String? // 预签的 approve 交易 raw hex（下单时 allowance 不足才需要，可空）

  // ---- Phase 2 预留（本次不启用，仅占位，迁移时回填） ----
  settlement_contract String? // Phase 2：结算合约地址（Phase 1 恒 null）
  order_nonce         Int?    // Phase 2：链上订单 nonce（用于撤单/防重放，Phase 1 恒 null）
  eip712_signature    String? // Phase 2：EIP-712 订单签名（替代 signed_swap_tx）

  // ---- 预留：卖单镜像、部分成交等后续字段 ----
  fill_kind       String    @default("fill_or_kill") // fill_or_kill（V1.4）；partial 预留

  @@index([user_address, created_at])
  @@index([status, expires_at])   // keeper 拉 pending + 过期清扫，避免全表扫描
  @@index([chain_id, token_in, token_out, status]) // keeper 按交易对分组盯价
  @@map("limit_orders")
}
```

### 3.2 精度铁律落地

| 字段 | 类型 | 语义 | 依据 |
| --- | --- | --- | --- |
| `amount_in` | `Decimal(78,0)` | 链上原始大整数（tokenIn 最小单位） | 铁律「金额 BigInt 定点」 |
| `min_amount_out` | `Decimal(78,0)` | 链上原始大整数（tokenOut 最小单位） | 铁律「金额 BigInt 定点」 |
| `limit_price` | `Decimal(78,18)` | 比率十进制字符串（tokenIn 每 tokenOut） | 铁律「比率十进制字符串」，与 `price_alerts.target_price` 同口径 |
| `slippage_bps` | `Int` | bps（1=0.01%） | 与 swap 的 `slippageBps` 一致 |

### 3.3 `min_amount_out` 的派生（权威值，禁 Float）

用户在前端只填 `amountIn`（人读）+ `limitPrice`（人读，如 "2500"）。后端用 BigInt 定点推导：

```
min_amount_out = floor( amount_in × 10^decimalsOut × 10^18 / ( limit_price_scaled × 10^decimalsIn ) )
其中 limit_price_scaled = parseDecimal(limit_price, 18)   // limit_price × 10^18，复用 dex/math
```

- **向下取整（floor）**：保证「市场价 ≤ limitPrice」时必然触发，且 `amountOutMin = min_amount_out` 永不高于用户的真实限价，不拒掉本应成交的单；误差 < 1 个最小单位。
- 推导只依赖 `token_in/token_out` 的 decimals（目录 `token-catalog` 优先，兜底 18，与 MarketService 同策略）。
- 存储时 `min_amount_out` 为**权威值**，`limit_price` 为展示值；成交/触发/预签交易三处都读 `min_amount_out`，不读 `limit_price`。

## 四、状态机

### 4.1 状态与迁移

```
                  ┌──────────────(user cancel, CAS)──────────► CANCELLED（终态）
                  │
                  │  ┌─────────(expires_at < now, keeper 清扫)► EXPIRED（终态）
                  │  │
PENDING ──────────┼──┼────────────────────────────────────────────┐
  │               │  │                                            │
  │(keeper 盯价，  │  │                                            │
  │ quote.amountOut│  │                                            │
  │ >= min_amount_out,                                            │
  │ CAS pending→triggered)                                        │
  ▼                                                                ▼
TRIGGERED ──(广播+回执 success)──► FILLED（终态，回填 swap_id/tx_hash）
  │
  ├──(回执 revert / nonce 失效 / 余额不足 / allowance 不足)──► FAILED（终态）
  └──(广播 RPC 失败且不可重试)──────────────────────────────► FAILED（终态）
```

- 终态：`filled` / `cancelled` / `expired` / `failed`。进入终态后不再迁移。
- `pending` 拆成两个子态（用 `signed_swap_tx` 是否有值区分，不新增状态枚举）：
  - `pending + signed_swap_tx = null` → **未武装（unarmed）**：keeper 跳过（等用户提交签名）。
  - `pending + signed_swap_tx != null` → **已武装（armed）**：keeper 参与盯价触发。

### 4.2 状态转换常量（与 `swap.types.ts` 同风格，后端直接实现）

```ts
export const LimitOrderStatus = {
  PENDING: 'pending', TRIGGERED: 'triggered', FILLED: 'filled',
  CANCELLED: 'cancelled', EXPIRED: 'expired', FAILED: 'failed',
} as const;

export const TERMINAL_LIMIT_ORDER_STATUSES = new Set([
  'filled', 'cancelled', 'expired', 'failed',
]);

export const LIMIT_ORDER_STATUS_TRANSITIONS = {
  pending:   new Set(['triggered', 'cancelled', 'expired', 'failed']),
  triggered: new Set(['filled', 'failed']),
  filled:    new Set(), cancelled: new Set(), expired: new Set(), failed: new Set(),
};
```

## 五、执行模型（关键风险点：交易由谁签名）

### 5.1 为什么不能「keeper 持钥签名」

官方 Router 的 `swapExactTokensForTokens / exactInputSingle` 内部逻辑是「从 `msg.sender` 把 `amountIn` 划进池子」（`safeTransferFrom(msg.sender, pair, amountIn)`）。

- 现在（正常 swap）：用户签名 → `msg.sender = user` → Router 从 user 划币（前提 user 已 approve Router）。
- 若 keeper 签名 → `msg.sender = keeper` → Router 只会从 keeper 划币，**用户的 `user→Router` allowance 完全不起作用**。

因此「keeper 持钥」要在第一阶段复用现有 allowance 模型，只有两条出路，都违背当前决策：

| 出路 | 代价 | 结论 |
| --- | --- | --- |
| 用户额外 approve keeper EOA 一笔精确额度，keeper 先 `transferFrom(user→keeper)` 再 swap | 授权对象从「不可变 Router」变成「可变热钱包」，非托管铁律被削弱；keeper 私钥被攻破即可抽走所有在挂订单额度；且多 1~2 笔交易 | ❌ 违背决策 2 与铁律 |
| 引入一个最小「结算合约」替代 keeper EOA 做授权对象 | 这就是第二阶段的自有合约，等于把 Phase 2 提前 | ⏸ 推迟到 Phase 2 |

### 5.2 推荐：用户预签 + keeper 广播（第一阶段）

**流程**：

```
1. 下单（POST /limit-orders）
   后端：复用 SwapService.prepare 取最新报价 + 查 allowance + 构造 Router calldata（amountOutMin=min_amount_out, recipient=user, deadline=expires_at）
   后端：ChainRpcService 补 nonce（getTransactionCount(user,'pending')）+ gas（estimateFeesPerGas/配置兜底）+ chainId
   返回「待签交易清单」：approval（如需）+ swap

2. 用户钱包签名（前端 wagmi，签名但【不广播】）
   签名顺序：approval（nonce=N）→ swap（nonce=N+1）

3. 提交签名（POST /limit-orders/:id/signature）
   后端校验：recoverAddress(signedTx) === user_address
             signedTx.to === 期望 Router 地址
             解码 calldata 的 amountIn / amountOutMin / recipient / deadline === 订单字段
   通过后存 signed_swap_tx / signed_approval_tx，订单进入 armed

4. keeper 盯价触发后广播：
   若 signed_approval_tx 存在 → 先广播 approval 并等回执 → 再广播 swap
   否则直接广播 swap
   广播 = eth_sendRawTransaction(signed_tx)，【无需任何私钥】，Gas 由 from=user 承担
```

**为什么这个模型是安全的（权限边界）**：

- keeper 手里**没有私钥**，只有一串「用户自己签好、且后端已校验过内容」的 raw tx。
- 这串 raw tx 是**自限定的**：`from=user`、`recipient=user`、`amountIn` 固定、`amountOutMin=min_amount_out`、`deadline=expires_at`。keeper 广播它最多只能让用户**以不低于限价的价格成交**，无法把币转到别处、无法多划额度、无法改金额。
- 因此「动不了用户本金」由**交易内容本身**保证，而不是靠 keeper 自觉。

### 5.3 该模型的已知局限（必须在文档与产品层明示，并由 Phase 2 根治）

| 局限 | 后果 | Phase 1 缓解 | Phase 2 根治 |
| --- | --- | --- | --- |
| **nonce 失效**：预签后用户又发其他交易，nonce 被占用 | 预签交易永远无法上链（nonce too low） | 广播失败即标记 `failed` + 通知用户重新下单；下单页提示「限价单生效期间请勿用同钱包高频操作」 | 链上订单用 `order nonce`（订单自增）替代账户 nonce，签名与账户 nonce 解耦 |
| **gas 固化**：签名时 gas 费写死 | gas 飙升→交易被套住；gas 回落后才能出块 | 下单时按「当前 + 一定上浮」签 EIP-1559 maxFee；仍可能过时 | filler 支付 gas 并从 output 扣费，实现 gas 竞价 |
| **deadline 需上界**：router 的 deadline 是 unix 秒 | 订单不能「永不过期」 | `expires_at` 必须有上界（如最长 7 天），且预签 deadline = expires_at，链上兜底过期 | 链上订单同样设 deadline，语义一致 |
| **撤单不可撤销签名字节**：DB 已存签名，极端情况下已被偷走的字节仍可被广播 | 理论上「取消」只是 keeper 不再广播，恶意广播仍可能成交 | 由 amountOutMin 自限（成交价仍不劣于限价，本质是用户当初的意愿）；如需硬撤，提示用户撤销对 Router 的授权（approve 0） | 链上 `cancelOrder(orderNonce)` 直接使签名失效 |

### 5.4 备选方案对比与取舍

| 维度 | 用户预签 + keeper 广播（推荐） | keeper 持钥 + 用户额外授权 keeper |
| --- | --- | --- |
| 与决策 2「复用现有 allowance(user→Router)」 | ✅ 完全一致 | ❌ 授权对象改为 keeper EOA |
| 非托管铁律 | ✅ 后端只存「用户签好的交易」，无任何私钥 | ⚠️ 后端持热钱包私钥，可抽干在挂额度 |
| 私钥泄露爆炸半径 | 无执行私钥 | 所有在挂订单额度之和 |
| 实现复杂度 | 中（需签名校验 + nonce/gas 处理） | 中（需私钥托管 + 多笔交易编排） |
| 用户 Gas | 用户承担 | keeper 承担（可做 gas 赞助，但需手续费机制） |
| 面向 Phase 2 的平滑度 | 高（订单语义 1:1 映射到链上 order struct） | 低（链下私钥模型到链上被废弃重写） |

**推荐**：用户预签 + keeper 广播。它是唯一「零执行私钥、复用现有 allowance、订单语义可直接映射到 Phase 2 链上订单」的第一阶段方案。非官感与铁律均不破。

## 六、keeper 盯价机制

### 6.1 轮询框架

复用 Indexer / SwapReconciler 的 `setInterval` 模式（**无** @nestjs/schedule、无 BullMQ、无 Redis）：

```ts
@Injectable()
export class LimitOrderKeeperService implements OnModuleInit, OnModuleDestroy {
  onModuleInit() { if (env LIMIT_ORDER_KEEPER_AUTOSTART==='true') this.start(); }
  start() { this.timer = setInterval(() => void this.runCycle(), interval); }
  runCycle() { await this.sweepExpired(); await this.scanAndFill(); }
}
```

- 间隔：`LIMIT_ORDER_KEEPER_INTERVAL_MS`，默认 `15_000`（15s，介于 Indexer 12s 与 Reconciler 30s 之间，兼顾及时性与 RPC 限流）。
- 单轮内有 `running` 防重入（同 Indexer 的 `scanning` 标志）。
- 提供手动触发 `POST /api/v1/limit-orders/keeper/run`（幂等，供测试/排障），与 Indexer 的 `/scan` 对齐。

### 6.2 如何筛「可能触发」的单（避免全表扫描）

三级漏斗：

1. **索引限定 pending 集**：`@@index([status, expires_at])`。查询 `where: { status: 'pending', signed_swap_tx: { not: null } }`（armed 才参与）。pending 是天然小集合（活跃挂单数），不必扫全表。
2. **按交易对分组，一次报价复用**：`SELECT DISTINCT chain_id, token_in, token_out FROM limit_orders WHERE status='pending' AND signed_swap_tx IS NOT NULL`。对每个 (chainId, tokenIn, tokenOut) 只做**一次参考报价**（如 `quoteBestForChain(chainId, tokenIn→tokenOut, referenceAmount)` 取即期价），把「当前价已劣于该对上**最优（最容易触发）**限价」的对整组跳过——大多数不活跃对在这一层就被剔除。
3. **逐单精确判定**：对通过第二层的每个订单，用**订单自己的 `amountIn`** 调 `quoteBestForChain(chainId, tokenIn→tokenOut, order.amountIn)`，判定 `amountOut >= min_amount_out` 才进入成交。

> 说明：第 2 层是优化，V1.4 MVP 若 pending 规模小，可简化为「armed pending 逐单精确报价」；但第 2 层的「按对分组」应保留在设计中，作为 pending 增长后的伸缩手段，避免「每单一次 RPC」的 O(订单数) 报价爆炸。

### 6.3 价格来源：用报价引擎 amountOut，不用 MarketService USD 价

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| `DexPoolService.quoteBestForChain`（amountOut） | ✅ 主用 | 触发、成交、预签 `amountOutMin` 三者同源同口径；且直接得到「当前能成交多少」，天然覆盖多池最优路径与滑点影响 |
| `MarketService.getTokenPrice`（USD 推导价） | ⚠️ 仅展示/通知 | 它经 token→USDC（或 token→WETH→USDC）链上推导，与「tokenIn→tokenOut 实际成交价」存在口径与路径差异，作触发源会误触发 |

触发判定（买单）：

```
currentAmountOut = quoteBestForChain(chainId, tokenIn→tokenOut, amountIn).amountOut
hit = currentAmountOut >= min_amount_out        // 等价于 市价 <= limit_price
```

卖单镜像（预留接口）：`tokenIn/tokenOut` 对调，`hit = currentAmountOut <= max_amount_out`。

## 七、防重复成交 / 幂等

价格瞬间反复穿越目标价时，三道闸保证一张单只成交一次：

1. **状态机 CAS 抢占（第一道，核心）**：触发用条件更新，只有抢到状态迁移的 keeper 实例继续：

   ```sql
   UPDATE limit_orders
   SET status='triggered', triggered_at=now()
   WHERE id=$1 AND status='pending';
   -- 受影响行数 === 1 才继续广播；=== 0 说明已被别的实例/线程抢占，跳过
   ```

   多实例部署（未来水平扩展）下此 CAS 是「只成交一次」的硬保证。
2. **确定性 tx hash（第二道）**：预签字节不变 → tx hash 不变。即使 CAS 与广播之间出现极端竞态把同一份 raw tx 广播两次，链上同一笔 tx 不可能被打包两次，天然幂等。
3. **`swaps.tx_hash` 唯一约束（第三道，DB 兜底）**：成交后 `submit()` 写 `swaps`，`tx_hash` 唯一；重复写库返回 409 而非重复记录。

> 注意：CAS 必须放在「触发判定之后、广播之前」。`triggered` 是「已抢占、正在广播」的中间态，用于持有锁；回执确认后迁移 `filled`，revert 则迁移 `failed`。切不可跳过 `triggered` 直接从 pending 写 `filled`，否则广播失败后无法回退。

## 八、撤单与过期

### 8.1 用户撤单

- `POST /api/v1/limit-orders/:id/cancel`（或 `PATCH`）：`UPDATE … SET status='cancelled' WHERE id=$1 AND user_address=$2 AND status='pending'`（CAS + 属主校验，返回行数 0 → 404/409）。
- 语义为「best-effort 取消」：keeper 不再广播。由于 §5.3 所述签名字节仍在，若需**硬撤销**，引导用户对 Router `approve(0)`（撤销授权），阻断任何后续 `transferFrom`。
- 撤单后落站内通知（`NotificationDispatcher`，type=`limit_order_cancelled`）。

### 8.2 过期

- keeper 每轮先 `sweepExpired()`：`UPDATE … SET status='expired' WHERE status='pending' AND expires_at < now()`。
- 链上兜底：预签交易 `deadline = expires_at`，即便过期单的签名被广播，Router 也会因 deadline 已过而 revert（链上最终兜底，不依赖 keeper 自觉）。
- 过期后通知用户（type=`limit_order_expired`）。

### 8.3 keeper 触发前的有效性重检

广播前必须复核订单仍处于可成交状态（防止 CAS 之后、广播之前被用户撤单/过期）：

```
再次读单 → 确认 status === 'triggered'（仍是自己抢到的态）
        → 确认 now < expires_at
        → 只读复核 balance >= amount_in 且 allowance >= amount_in（不足则 FAILED + 通知，不广播注定 revert 的交易浪费 gas）
```

### 10.1 数据模型字段预留（已在 §3.1 标注）

### 10.3 语义延续

- 「限价 = amountIn / minAmountOut」在链上仍以 `makingAmount / takingAmount` 表达，触发判定逻辑从「链下报价 amountOut」变成「链上结算合约内部校验」，**订单字段零语义漂移**。
- 链上阶段新增：执行者激励（filler 抽成）、MEV 抗性（允许 filler 抢单、私有 RPC/Flashbots）、硬撤单（nonce 失效）、Gas 由 filler 支付。

## 十一、风险清单

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 1 | **keeper 单点故障**（进程挂了→无人盯价成交） | 订单全部停滞 | 与 Indexer/Reconciler 同模式 + 手动触发端点 + 健康检查接入现有异常中心（AnomalyEvent）；未来可独立进程/多实例（CAS 已保证多实例安全） |
| 2 | **执行私钥泄露** | Phase 1 **不存在执行私钥**（用户预签、keeper 纯广播）。此风险推迟到 Phase 2 filler 密钥：HSM/KMS、env 注入、最小权限、轮换 | 见 §5.4 |
| 3 | **价格来源滞后** | 误触发/漏触发 | 触发用实时 `quoteBestForChain`（不读旧 `market_snapshots`）；成交前复核；`amountOutMin` 链上兜底 |
| 4 | **Gas 波动** | 预签 gas 过时→交易滞留/不成交 | 下单签「当前价 + 上浮」的 EIP-1559 maxFee；滞留单标记 failed 并通知重签；Phase 2 filler 竞价根治 |
| 5 | **nonce 失效** | 预签交易永久失效 | 广播失败识别 `nonce too low` → failed + 通知重新下单；下单页明示 |
| 6 | **MEV / 抢跑（sandwich）** | 用户成交价被夹在限价边缘 | `amountOutMin=限价` 保证不劣于限价；最优路径路由；Phase 2 接私有 RPC + filler 竞价 |
| 7 | **撤单不可撤销签名字节** | 极端场景被广播 | 语义 best-effort；`amountOutMin` 自限（成交不劣于限价）；硬撤引导 `approve(0)`；Phase 2 `cancelOrder(nonce)` |
| 8 | **成交时余额/授权不足** | 预签交易 revert | 广播前只读复核 balance/allowance，不足直接 failed + 通知，不广播注定 revert 的交易 |
| 9 | **签名校验漏洞**（存储了被篡改的 raw tx） | keeper 广播错误交易 | 提交签名时 `recoverAddress` + 逐字段比对 calldata，非用户签名或内容不符一律拒绝存储 |
| 10 | **DB 中 raw tx 泄露** | 攻击者广播「用户已授权、以限价成交」的交易 | 该交易自限（from=user、recipient=user、限价），最坏即按用户当初意愿成交；Phase 2 换 EIP-712 签名 + 链上 nonce 硬失效 |
