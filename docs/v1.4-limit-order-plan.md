# VORTEX DEX — V1.4 限价单（Limit Order）立项

> 版本：V1.4 · 日期：2026-11-06 · 状态：已立项，进入开发
> 架构基线：`docs/v1.4-limit-order-architecture.md`（本立项文档是其执行摘要，冲突以架构文档为准）

## 一、决策记录（技术负责人拍板）

1. **路线**：学 1inch/Matcha，走「自有合约」终极形态，分两步：
   - **Phase 1（本次开发）**：链下 keeper——订单存 PostgreSQL，用户预签成交交易，keeper 盯价满足即广播。
   - **Phase 2（预留，不做）**：订单迁到链上结算合约 + filler 执行者激励。
2. **资金托管**：下单不锁币，成交时从用户钱包划走，复用现有 `user → Router` allowance。
3. **范围**：先做「限价买单（limit buy）」，卖单镜像接口预留。
4. **执行签名模型（架构关键结论）**：**用户预签 + keeper 广播**，否决 keeper 持钥。
   - 硬约束：官方 Router 从 `msg.sender` 划币，keeper 持钥无法动用用户已授权额度。
   - 结果：**Phase 1 零执行私钥**，keeper 只广播用户签好的 raw tx（`eth_sendRawTransaction`，无需私钥，Gas 由 user 承担）。

## 二、数据模型（摘要）

新增 `LimitOrder` 表（详见架构 §三），核心字段：
- 订单：`user_address` / `chain_id` / `direction`(buy) / `token_in` / `token_out`
- 金额：`amount_in` Decimal(78,0) / `min_amount_out` Decimal(78,0)（**权威限价**）/ `limit_price` Decimal(78,18)（仅展示）
- 生命周期：`status`(pending/triggered/filled/cancelled/expired/failed) / `expires_at` / `triggered_at` / `filled_at`
- 成交：`swap_id` / `tx_hash` / `failure_reason`
- 预签：`signed_swap_tx`（raw hex）/ `signed_approval_tx`（可空）
- Phase 2 预留：`settlement_contract` / `order_nonce` / `eip712_signature`

`min_amount_out` 派生（BigInt floor，禁 Float）：
`min_amount_out = floor( amount_in × 10^decimalsOut × 10^18 / ( limit_price_scaled × 10^decimalsIn ) )`

## 三、状态机

```
PENDING ──(keeper 盯价 quote.amountOut >= min_amount_out, CAS)──► TRIGGERED
  │(user cancel, CAS)──► CANCELLED（终态）
  │(expires_at<now, keeper 清扫)──► EXPIRED（终态）
TRIGGERED ──(广播+回执 success)──► FILLED（终态）
          ──(revert/nonce失效/余额不足/allowance不足)──► FAILED（终态）
```

armed = `signed_swap_tx != null`，keeper 只盯 armed 单。

## 四、幂等（防一张单成交两次，三道闸）

1. CAS 抢占：`UPDATE ... SET status='triggered' WHERE id=$1 AND status='pending'`，影响行数===1 才继续。
2. 确定性 tx hash：同一签名字节 → 同一 tx，链上天然不重复。
3. `swaps.tx_hash` 唯一约束兜底。

## 五、API 契约（摘要，详见架构 §九）

- `POST /api/v1/limit-orders` — 下单，返回 `order` + `signingPayload`（待签交易清单）
- `POST /api/v1/limit-orders/:id/signature` — 提交签名（recover 校验 + calldata 比对），订单 armed
- `GET /api/v1/limit-orders?user=:address&status=...` — 列表
- `GET /api/v1/limit-orders/:id` — 详情
- `POST /api/v1/limit-orders/:id/cancel` — 撤单（CAS + 属主校验）

## 六、对现有代码的改动面

- 新增：`apps/api/src/modules/limit-order/`（controller/service/types/signer/keeper/executor）
- 改动（最小）：`SwapModule.exports` 加 `SwapService`（一行）；`Notification.type` 扩 `limit_order_*`；Prisma 迁移加 `LimitOrder`；`ChainRpcService` 加 `sendRawTransaction` 薄封装。
- 复用：`DexPoolService.quoteBestForChain`、`SwapService.prepare/tryReadReceipt`、`Erc20ReaderService`、`NotificationDispatcher`、`dex/math`、Indexer 的 setInterval 范式。

## 七、派工顺序（后端先行，前端随后，测试收尾）

1. **后端骨架**：schema + 迁移 + limit-order 模块骨架 + 状态机常量/单测
2. **后端核心**：下单（派生 min_amount_out + 构造待签交易）+ 签名校验（recover + calldata 比对）
3. **后端 keeper**：盯价循环 + 触发判定 + 成交广播 + 幂等 CAS + 撤单/过期 + 通知接线
4. **前端**：下单页 + 钱包签名（不广播）+ 挂单列表 + 撤单 + 成交历史
5. **测试验收**：后端单测 + 前端组件 + 端到端（模拟 keeper 触发）

## 八、验收标准（关键测试点）

- `min_amount_out` 取整方向正确（floor，BigInt 单测）
- 签名校验：拒绝非本人签名、拒绝 calldata 内容不符
- CAS 幂等：多实例只成交一次
- 过期链上兜底：预签 deadline=expires_at，过期签名被广播也 revert
- 非托管：keeper 无执行私钥，raw tx 自限（from=user、recipient=user、amountOutMin=限价）

## 九、已知局限（Phase 1 明示，Phase 2 根治）

nonce 失效 / gas 固化 / deadline 需上界 / 撤单不可撤销签名字节——详见架构 §5.3，均有 Phase 1 缓解 + Phase 2 根治方案。
